# Institutionalization — audit and implementation plan

Started 2026-09-29 against `main` at 1.0.14 (+ PR #57, 1.0.15). This file is
the working checklist for turning NOSHASHI into a product an executive,
compliance officer, analyst, developer or auditor can understand and trust.
It is updated as phases land; every line says what exists in the code today,
not what is intended.

Status words used throughout: **EXISTS** (implemented, in the app),
**PARTIAL** (implemented in part; the gap is named), **GAP** (not built),
**WRONG** (built, but misleading or unsafe; fix before pitching).

---

### 1.2 Against the master prompt, pillar by pillar

**Compliance**
- GO / HOLD / NO-GO from a deterministic rule set with five check states (PASS, FAIL, REVIEW, INSUFFICIENT_DATA, NOT_APPLICABLE) — EXISTS.
- Institutional policies: versioned, canonical hash, draft → pending → active → archived, four-eyes enforced by a table constraint and a trigger (author ≠ activator) — EXISTS. Shown since Phase 3 as Draft / In review / Approved & active / Superseded; approval and activation are one four-eyes step.
- Exceptions with requester ≠ decider (constraint), evidence requests, audit rows — EXISTS. Expiry on every approval since Phase 3.
- Travel Rule, HHI, counterparty share, reserve headroom, strict freeze as policy thresholds that feed the verdict — EXISTS (`policy.ts`, `desk/rules.ts`); each needs its "what it affects / when it triggers" line surfaced in the policy editor — PARTIAL.
- Credentials and permissioned domains — EXISTS (real mainnet directory since 1.0.15).
- **WRONG:** the verification gate, the tray, Mission Control and the Desk still select from `DOMAIN_REGISTRY`, six illustrative "reference domains" with invented institution names and member counts. They are rule profiles, not ledger domains, and must be presented as such (names, no fabricated members) or replaced with real domains.

**Liquidity**
- Order-book depth, *backed* depth vs quoted, AMM state and pool governance, exit simulation, stress schedule — EXISTS (`desk/book.ts`, `desk/liquidity.ts`, `desk/amm.ts`, `desk/stress.ts`).
- The quoted-vs-fillable distinction is computed but not the headline everywhere — PARTIAL.

**Evidence**
- Receipt digest over a canonical body, policy version bound into it — EXISTS.
- Verify a stored receipt (recompute and compare; UNVERIFIABLE is never shown as verified) — EXISTS.
- Export: CSV / signed export on Ledger & Policy, audit-trail CSV + SHA-256 manifest (1.0.15), admission records — EXISTS.
- **GAP:** *replay* — re-read the ledger at the receipt's ledger index, re-run the same policy version, and show the difference from the recorded result.
- **GAP:** an institutional report (executive summary → decision → findings → evidence → verification instructions) as one exportable document.

**Data validation**
- Multi-node agreement exists as its own screen (Ledger Sync), and since Phase 3 is attached to every recorded verdict (SOURCE_AGREEMENT). *Remaining:* the live posture indicators (tray, Mission Control, status rail) evaluate the rules without it; they are indicators, not recorded verdicts, and carry no receipt.

**AI**
- Governance rules (never signs, never issues verdicts, figures only from readings with a ledger index) — EXISTS in prompts and NOSHX Core. **PARTIAL:** answers cite sources in text; there is no structured citation object the UI can link to evidence.

**Enterprise**
- Roles, RLS on every `noshashi` table, audit log with actor/action/target, API keys with lifecycle audit, rate limits, signed webhooks, OpenAPI-style reference (`docs/API.md`, `/docs/api/`) — EXISTS.
- **GAP:** *reviewer* and *auditor* are not distinct roles (regulator ≈ read-only auditor); SSO is not implemented.

**Product surface**
- 30+ scenes in one sidebar, grouped under 8 headings — **WRONG for a first-time institutional user**: no progressive disclosure, no executive view, no single decision card.
- The customer-facing app links to a "Business plan" (the vendor's revenue model, with a hard-coded XRP price default). Not something a bank should see in the product. **WRONG**.

**Release / platform**
- Builds for macOS (arm64, x64), Windows (msi, nsis), Linux (deb, rpm, AppImage) with updater signatures — EXISTS.
- **Production blocker:** builds are not code-signed (Apple Developer ID) or notarised, nor Authenticode-signed. The workflow has no signing inputs yet. Needs credentials only the owner can obtain.

**Repository hygiene**
- `backend/` (Python FastAPI: Polygon, "QuantPad", sentiment services) and `frontend/` (Next.js) are an earlier product, never deployed (`scripts/vercel-ignore-build.sh` says so), still compiled by CI. They contradict the product story a due-diligence reviewer reads. **WRONG** to leave unexplained.
- Root clutter: `Unknown.png`, `noshashi-outreach.zip`, two `.code-workspace` files, `docker-compose.yml` and `nginx.conf` for the unused backend.
- `README.md` says "Last updated 2026-09-10" and predates a month of releases. **WRONG**.

**Security (first pass)**
- `npm audit --omit=dev`: 0 vulnerabilities. No live secrets in the tree (`.env.example` placeholders only). CSP is strict (no `unsafe-eval`, no remote scripts); `connect-src` lists local model ports on purpose (Ollama, LM Studio, llama.cpp, …).
- Tauri capabilities are narrow; `core:webview:allow-internal-toggle-devtools` is granted in production — review.
- Stripe and org webhooks are signature-verified; Edge Functions re-check entitlements server-side.
- Documentation of all this for a procurement reviewer: **GAP** (`SECURITY.md` exists at the root; no threat model, data-governance or procurement pack).

### Things this plan will not do

- Claim certifications (SOC 2, ISO 27001), customers, SLAs or guarantees that do not exist. Procurement docs mark them PLANNED.
- Let the AI decide. Every verdict stays a function of ledger state and a policy version.
- Show data that was not read. Where a figure is illustrative it is labelled, and removed from anything an institution could mistake for a reading.
- Sign releases without the owner's certificates. The workflow is prepared; the credentials are the owner's to add.
